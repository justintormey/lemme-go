# LemmeGo QA — 2026-09-02

Full pre-TestFlight audit of v1.1.1, landing as v1.2.0.

Method: 11 parallel auditors over the Swift sources and project config, each finding
then checked by two independent adversarial verifiers (one asked to refute it from the
code, one asked whether a real beta tester would ever hit it). 103 agents, 46 raw
findings, **28 confirmed, 18 refuted**. Everything below that says "fixed" was fixed
and verified by a passing build; nothing here was taken on an agent's word alone.

Build state after this pass:
- Simulator build: **succeeds, zero compiler warnings** (was 1)
- Unit tests: **50 pass** (was 0 executed, see B1)
- Release archive: **succeeds** (was: could not archive at all, see B2)
- App Store export and distribution signing: **succeeds**

## Build blockers found and fixed

**B1. The test suite never ran.**
The shared scheme's `<Testables>` block was empty. `Cmd+U` and `xcodebuild test`
executed zero tests and reported success. This is the most consequential finding in
the audit, because it is what hid C2: the moment the suite was wired up, an existing
test failed and exposed a live bug that had been sitting in a committed test file,
unread, since the tests were written.

**B2. `DEVELOPMENT_TEAM` was empty**, so `xcodebuild archive` failed at
`GatherProvisioningInputs` with "Signing for LemmeGo requires a development team."
The project could not produce a distributable build at all. Set to `5Y8S56DTEH`.

## Correctness bugs found and fixed

**C1. Screen Time read as denied on iOS 26.4+.** `AppBlockingManager.checkAuthorization()`
handled `.approved`, `.denied` and `.notDetermined`, then sent everything else to
`@unknown default → isAuthorized = false`. iOS 26.4 added `.approvedWithDataAccess`,
an approved state, which landed in that fallback. On current iOS the app would refuse
to start any lock for a user who had granted permission.

This surfaced as a *compiler warning*, not an error, which is why it survived: Swift
downgrades an inexhaustive switch to a warning when `@unknown default` is present, and
names the missing case in a note. The warning had been in the build output.

**C2. Emergency-unlock budget reset a day early.** `Calendar.startOfWeek(for:)` derived
the week from `.yearForWeekOfYear`/`.weekOfYear`. `Calendar.date(from:)` anchors that on
the calendar's locale-dependent `firstWeekday`, which is Sunday in en_US, so a Sunday
resolved to the *following* Monday. A user who spent all five unlocks Monday through
Saturday got a fresh five on Sunday, then another five on Monday. The commitment
mechanism, which is the product, silently doubled every week.

Now counted back from the date's own weekday, which is locale-independent, stepping in
whole days from `startOfDay` so DST transitions are safe. Four regression tests cover
every weekday, a Sunday-first calendar, and a month boundary. **All four were confirmed
to fail against the old implementation before being accepted.**

**C3. Crash starting a zero-length session.** All three duration wheels at 0 with
Unlimited off produced `UNTimeIntervalNotificationTrigger(timeInterval: 0)`, whose
interval must be greater than zero; it raises an `NSInvalidArgumentException` that Swift
cannot catch. Reachable from the UI in about three seconds.

**C4. A lock could engage while blocking nothing.** Starting a session validated only
Screen Time authorization. With no apps selected, the app showed the full "Phone Locked"
screen and demanded an NFC tag to escape while shielding zero apps: all of the friction,
none of the product.

**C5. A corrupted blocked-app list was indistinguishable from an empty one.** A decode
failure in `BlockedAppsStore` silently fell through to an empty selection with only a
`print`, producing exactly the unenforced lock in C4 with no signal anywhere. The store
now reports load failure separately from "the user picked nothing", and the two produce
different messages.

C3, C4 and C5 were one design gap: `startLockSession` committed to a session without
checking that it was meaningful or enforceable. The two near-identical start functions
are now one validated implementation returning a typed `LockStartFailure`, so the UI
states the real reason instead of always blaming Screen Time.

**C6. "Lock Now" could strand a user holding a valid tag.** A remote session borrows
`registeredChips[0]` as an identifier, and unlocking required that exact tag even though
no tag started the session. With two tags registered, holding the wrong one produced
"Wrong tag! Use the tag that started this session" for a session no tag had started. Any
registered tag now releases a remote session; NFC-started sessions still require theirs.

**C7. Turning Screen Time off mid-session was invisible.** `reapplyShields()` no-opped
silently while the UI kept showing an enforcing lock. The session is deliberately *not*
ended, because ending it would make revoking Screen Time a one-tap bypass, but the lock
screen now says apps are no longer blocked.

**C8. Emergency unlock failed silently at zero budget.** Tapping Unlock with none
remaining did nothing at all, with no feedback.

**C9. `NaN` progress-bar geometry** from a zero-duration session. Guarded and clamped.

**C10. The unlock notification claimed something untrue.** It read "Apps are now
unlocked!" It fires while the app is suspended, when nothing has run to drop the
shields, so the apps are still blocked when the user reads it. It now says to open
LemmeGo, which is what actually clears them. See O1.

**C11. Blank tag name discarded the registration.** Clearing the prefilled name and
tapping Save dismissed the alert without registering, leaving a first-run user stuck on
the setup screen with no explanation.

**C12. The lock-screen starfield jumped once a second** for the entire session. The
positions were an instance `let` with a comment saying it existed to prevent exactly
that; SwiftUI rebuilds the struct on every parent render, and the lock screen renders
every second. Now `static let`.

**C13. Duration reset to 1h after every lock cycle.** `ContentView` swaps `MainView` out
for `LockScreenView` during a session, discarding its `@State`. Now persisted.

**C14. Stacked error timers wiped newer messages early.** Each NFC error scheduled an
unconditional 5-second clear, so an older timer erased a newer error. The clear now
fires only if the same message is still on screen.

## Config and submission gaps found and fixed

- **No privacy manifest.** The app uses `UserDefaults`, a required-reason API. Without
  `PrivacyInfo.xcprivacy` an upload draws an ITMS-91053 notice. Added, declaring zero
  collected data types, no tracking, and `CA92.1`. Verified present in the exported IPA.
- **No `ITSAppUsesNonExemptEncryption`**, so every upload paused to ask about export
  compliance. Set to `false`, which is literally true: the app performs no cryptography.
- **`NSUserNotificationsUsageDescription`** is not a real Info.plist key, so iOS never
  displayed it, and its text described scheduled sessions, a feature that does not
  exist. Removed.
- **`UIRequiredDeviceCapabilities = [armv7]`** corrected to `arm64`. Worth recording
  that this was *not* a submission risk: the build system already rewrote it to `arm64`
  at package time, confirmed by inspecting the shipped IPA. Source hygiene only.
- **Hardcoded `"1.1.1"` on the Settings About row.** Now reads `CFBundleShortVersionString`
  and `CFBundleVersion` from the bundle. It had already gone stale once before.

## Open, not fixed

**O1. Shields stay applied past session end while the app is backgrounded.** *(high)*
The only things that end a timed session are the in-process 1-second `Timer` and the
foreground/launch handlers. iOS suspends the app within seconds of backgrounding, which
is the normal way to use it, so at expiry nothing runs and the apps stay shielded until
the user next opens LemmeGo.

Self-heals in about a second when the user taps the notification, because that
foregrounds the app. Not fixed here because the real fix is a **DeviceActivityMonitor
app extension** with a `DeviceActivitySchedule` whose `intervalDidEnd` clears the store.
That means a new target, its own bundle ID and entitlement, and its own provisioning. It
is a feature-sized change and an architecture decision, not a QA patch.

Telling detail: `DeviceActivity.framework` is *already linked* to the app target while
no Swift file imports it, and the project declares only two targets. Someone started
down this road and stopped.

Mitigated for now by C10, so the notification no longer asserts something false.

**O2. The system clock is trusted for everything.** *(medium)*
Rolling the clock forward ends any timed session immediately and clears the shields, at
no NFC or emergency-unlock cost. Rolling it past the next Monday refills an exhausted
emergency budget. Both are Settings > General > Date & Time, roughly fifteen seconds.

A real fix needs a monotonic reference that survives termination, and there is no clean
one on iOS without a server. Worth deciding whether it matters: LemmeGo is a commitment
device for someone who wants to be committed, not a security control against its own
user. Recommend documenting rather than engineering around.

**O3. ISO7816 UID stability is not guaranteed.** *(medium)*
Some contactless payment cards randomise their UID per tap. Registering one appears to
work, then unlocking with the same physical card fails forever. Only reachable if the
user registers a payment card rather than a tag, which the TestFlight reviewer notes now
recommend they do. Called out explicitly in those notes as a caveat.

**O4. No escape if the tag is lost and the budget is spent, during an unlimited session.**
*(medium)* Unlimited sessions never expire, `Settings` is unreachable from the lock
screen, and with zero emergency unlocks the only way out is deleting the app. That does
work, because the shields live in the app's own named `ManagedSettingsStore`, but no
in-app copy tells the user so. Cheapest fix is a line of text on the lock screen at zero
budget. Worth doing before external testers see it.

**O5. Shield "verification" cannot detect failure.** *(low)*
`blockSelectedApps` writes `store.shield.applications`, then reads the same property
back and reports success. That checks the setter, not enforcement, and will report
success for stale opaque tokens after a reinstall or device restore. The diagnostic on
the lock screen is therefore weaker than it looks.

**O6. Tests wipe real app data.** *(low, developer-facing)*
All three test classes call `UserDefaults.standard.removeObject` in `setUp`/`tearDown`,
which is the same defaults domain the shipped app uses. Running `Cmd+U` on a simulator
where you have been using LemmeGo destroys your registered tags, blocked-app selection
and emergency-unlock history. Proper fix is injecting a `UserDefaults` instance into
`BlockedAppsStore` and `EmergencyUnlockTracker`. Deliberately deferred: it changes
production signatures for test isolation and deserves its own pass.

**O7. Session restore and shield teardown have no test coverage.** *(low)*
The highest-risk behavior in the app, restoring a session after the process is killed
and clearing shields on every exit path, is untested. Both need `LockManager`, which
needs Screen Time, so this needs the same dependency injection as O6.

**O8. Minor, documented, not fixed:** multiple tags in the NFC field picks an arbitrary
one; the `.feliCa` switch case is unreachable because polling never enables FeliCa; an
auto-expiry racing an in-flight unlock scan shows a spurious "Wrong tag!"; the Settings
permission-check `Timer` stalls while the tag list is scrolled; `reapplyShields()` can
race `AppBlockingManager`'s 0.5s authorization settle on cold launch.

## Not reproducible

18 of 46 findings were refuted by verification and are not listed as issues. The
recurring pattern was auditors asserting Apple framework behavior they had not checked,
or reporting a hazard that a guard elsewhere in the file already handled.

## The gap that matters most

**None of this has run on an iPhone.** Everything above was established by building,
archiving, exporting, and running the unit suite. NFC does not exist in the Simulator
and Screen Time cannot be meaningfully exercised there, so the two most important fixes
(C1 and C2) are both in code paths that only execute on a real device with Screen Time
granted.

C1 in particular fixes a bug whose entire symptom is "the app refuses to lock on current
iOS." Confirming it on hardware, once, is worth more than the rest of this document.
